Твой бэкенд представляет собой **двухкомпонентную микросервисную архитектуру**, которая выглядит очень достойно для MVP или уверенной беты. У тебя есть четкое разделение зон ответственности:

1.  **Java (Spring Boot)** — Основной API-шлюз. Отвечает за бизнес-логику, авторизацию (JWT), работу с базой данных (JPA), маршрутизацию файлов и отдачу статистики фронтенду.
2.  **Python (FastAPI)** — Тяжелый воркер для ML/AI задач. Отвечает за распознавание речи (Vosk), поиск персональных данных (Natasha) и аудио-процессинг (Pydub для вырезания ПДн).

Ниже представлен **подробнейший разбор** готового функционала, архитектуры и исчерпывающая документация по API для фронтенд-разработчика.

### 🟢 1. Уже готовый и работающий функционал

Исходя из предоставленного кода, у вас **полностью реализован следующий пайплайн**:

- **Система аутентификации:**
  - Регистрация и логин пользователей с хэшированием паролей (BCrypt).
  - Защита маршрутов с помощью JWT-токенов (срок жизни 24 часа).
- **Загрузка аудио (Аудио-шлюз):**
  - Прием аудиофайлов, их локальное сохранение (`uploads/original`).
  - Асинхронная передача файлов на обработку (пользователь не ждет окончания распознавания, запрос сразу возвращает `callRecordId`).
- **Транскрибация (Speech-to-Text):**
  - Конвертация любого аудио в нужный формат (PCM 16kHz Mono) "на лету" через Pydub.
  - Распознавание речи локальной моделью Vosk.
- **DLP / PII Анализ (Поиск персональных данных):**
  - Использование библиотеки `Natasha` для интеллектуального поиска ФИО (с учетом морфологии русского языка и списка исключений `STOP_NAMES`).
  - Кастомная логика для поиска номеров телефонов, дат и цифр (алгоритм поиска соседей-цифр).
- **Анонимизация данных (Цензурирование):**
  - **В тексте:** Замена найденных персональных данных на плашку `[ДАННЫЕ УДАЛЕНЫ]`. Текст склеивается в удобные чанки по 15 слов.
  - **В аудио:** Физическое "заглушение" (mute) фрагментов аудиозаписи, где звучат персональные данные. Генерация нового `.wav` файла в папку `uploads/redacted`.
- **Хранение и статистика:**
  - Сохранение диалога в БД с таймкодами (`startTime`, `endTime`) и привязкой типов ПДн (например, `NAME`, `CONTACT_INFO`).
  - Генерация агрегированной статистики по найденным утечкам для пользователя.
- **CORS:** Настроен глобально, фронтенд может стучаться с любого домена (удобно для разработки).

### 🟡 2. Жизненный цикл обработки звонка (Важно для фронтенда!)

Фронтенд должен понимать, что процесс долгий. У записи (`CallRecord`) есть статусы (`status`):

1.  `UPLOADED` — Файл только что загружен.
2.  `TRANSCRIBING` — Началась обработка (STT + вырезание слов в Python).
3.  `COMPLETED` — Обработка успешно завершена, можно запрашивать текст и аудио.
4.  `ERROR` — Произошла ошибка.

_Совет фронту:_ После загрузки файла, нужно делать поллинг (polling) — раз в 3-5 секунд дергать метод `GET /api/calls/{id}`, пока статус не станет `COMPLETED`.

### 🔵 3. API Документация для Frontend-разработчика

Базовый URL: `http://<адрес_сервера>:8080/api`
Все эндпоинты (кроме `/auth/**`) требуют заголовок:
`Authorization: Bearer <твой_jwt_токен>`

#### 🔐 3.1. Авторизация (Auth)

**1. Регистрация**

- **URL:** `POST /auth/register`
- **Тело запроса (JSON):**
  ```json
  {
    "login": "user@example.com",
    "password": "mysecretpassword",
    "name": "Иван Иванов",
    "company": "Рога и Копыта"
  }
  ```
- **Успешный ответ (200 OK):**
  ```json
  {
    "token": "eyJhbGciOiJIUzI1NiJ9..."
  }
  ```
- **Ошибки:** `409 Conflict` (логин занят), `400 Bad Request` (пустой логин/короткий пароль).

**2. Авторизация (Вход)**

- **URL:** `POST /auth/login`
- **Тело запроса (JSON):**
  ```json
  {
    "login": "user@example.com",
    "password": "mysecretpassword"
  }
  ```
- **Успешный ответ (200 OK):** Возвращает такой же JSON с `token`.
- **Ошибки:** `401 Unauthorized` (неверный логин или пароль).

#### 📞 3.2. Работа со звонками (Calls)

**1. Загрузка файла звонка**

- **URL:** `POST /calls/upload`
- **Content-Type:** `multipart/form-data`
- **Тело запроса (Form Data):**
  - Ключ: `file` (тип: File, форматы: mp3, wav, ogg)
- **Успешный ответ (200 OK):**
  ```json
  {
    "message": "Файл принят в обработку",
    "callRecordId": 15
  }
  ```

**2. Получить список всех звонков текущего пользователя**

- **URL:** `GET /calls/my`
- **Успешный ответ (200 OK):** Массив объектов звонков (сортировка от новых к старым).
  ```json
  [
    {
      "id": 15,
      "originalAudioPath": "uploads/original/uuid-123.mp3",
      "durationSeconds": 120,
      "status": "COMPLETED",
      "createdAt": "2023-10-27T15:30:00"

    {
      "id": 16,
      "originalAudioPath": "uploads/original/uuid-456.wav",
      "durationSeconds": null,
      "status": "TRANSCRIBING",
      "createdAt": "2023-10-27T16:00:00"
    }
  ]
  ```

**3. Получить детали конкретного звонка (с текстом транскрибации)**

- **URL:** `GET /calls/{id}` (например, `/calls/15`)
- **Успешный ответ (200 OK):**

#### 🎧 3.3. Аудио Плеер (Медиа)

Эти эндпоинты возвращают **байтовые потоки аудиофайлов**. Фронтенд может напрямую вставлять эти URL в тег `<audio src="..." />`, но так как нужна JWT авторизация, фронту придется либо скачивать файл через `fetch` как Blob, либо бэкенду нужно сделать эти руты открытыми (подумайте об этом!).

### 🧠 4. Архитектурный разбор и "Узкие места" (Для Backend-разработчика)

Код написан хорошо, но чтобы проект перешел из состояния MVP в Production-ready, нужно учесть следующие моменты:

**1. Взаимодействие Java и Python (Критическое место)**

- **Как сейчас:** В Java классе `TranscriptionService` используется блокирующий `RestTemplate.postForObject` внутри асинхронного потока (`@Async`). Если Python-сервер обрабатывает файл 10 минут, поток в Java будет "висеть" 10 минут, ожидая HTTP ответа. Если файлов закинут 100 штук, ThreadPool (настроенный на 4 потока в `AsyncConfig`) забьется, и остальные будут ждать в очереди, а HTTP-соединения могут отвалиться по таймауту.
- **Как нужно (в будущем):** Использовать Message Broker (RabbitMQ или Kafka). Java кидает сообщение "Обработай файл X", а Python слушает очередь. Когда Python закончит, он кидает сообщение обратно "Файл X готов", и Java обновляет базу. Либо Python может дергать Webhook URL в Java сервере.

**2. Разделение спикеров (Diarization)**

- Сейчас в `python-stt/app/transcription.py` искусственно задано `segments.append({"speaker": 1...})`. Vosk из коробки плохо разделяет голоса в одноканальном аудио.
- **Решение на будущее:** Использовать библиотеку `pyannote.audio` в Python для диаризации перед или после работы Vosk, либо перегонять стерео-записи, разбивая каналы на спикера 1 (оператор) и спикера 2 (клиент).

**3. Файловая система (Docker Volume)**

- Сейчас код плотно завязан на том, что папка `/uploads` расшарена между Java и Python контейнерами.
- Пути в БД сохраняются абсолютные/локальные (`uploads/original/...`).
- **Для масштабирования:** Лучше переделать `AudioStorageService` на работу с S3-совместимым хранилищем (MinIO, Yandex Object Storage). Java загружает в S3 -> отдает Python'у ссылку на S3 -> Python скачивает, обрабатывает, грузит `redacted.wav` в S3 -> отдает ссылку обратно в Java.

**4. Идентификаторы PII (Баг/Улучшение)**

- В Java сущности `TranscriptSegment` `piiTypes` хранится как строка через запятую. Если типов нет, будет пустая строка. При отдаче фронту `Arrays.asList(s.getPiiTypes().split(","))` из пустой строки сделает массив с одним элементом `[""]`. В коде контроллера это частично учтено (проверка `!s.getPiiTypes().isEmpty()`), но лучше хранить это в связанной таблице, либо использовать тип JSONB (если БД PostgreSQL).

### 1. Как устроены запросы для фронтенда

У тебя один эндпоинт, где тип аудио регулируется переменной в пути (`{type}`):

- **Оригинальное (загруженное) аудио:**
  `GET /api/calls/{id}/audio/original`
  _(Доступно сразу после успешной загрузки)_

- **Анонимизированное (очищенное) аудио:**
  `GET /api/calls/{id}/audio/redacted`
  _(Появляется только когда `status` изменится на `COMPLETED`)_

### 2. Разбор логики на бэкенде

Давай заглянем в твой код `CallController.java`, чтобы увидеть, как это происходит:

```java
@GetMapping("/{id}/audio/{type}")
public ResponseEntity<Resource> getAudio(@PathVariable Long id, @PathVariable String type) {
    CallRecord record = getCallWithSecurityCheck(id); // 1. Проверяем, что звонок твой

    // 2. Выбираем путь к файлу на основе параметра 'type'
    String path = "redacted".equalsIgnoreCase(type)
                  ? record.getRedactedAudioPath()
                  : record.getOriginalAudioPath();

    if (path == null) {
        throw new ResponseStatusException(HttpStatus.NOT_FOUND, "Файл отсутствует");
    }

    try {
        Path filePath = Paths.get(path);
        Resource resource = new UrlResource(filePath.toUri());

        // 3. Отдаем файл как аудио-поток
        return ResponseEntity.ok()
                .contentType(MediaType.parseMediaType("audio/wav"))
                .body(resource);
    } catch (Exception e) {
        throw new ResponseStatusException(HttpStatus.INTERNAL_SERVER_ERROR, "Ошибка чтения аудио");
    }
}
```

### 3. Важные моменты для фронтенда:

1.  **Формат ответа:** Бэкенд возвращает бинарные данные с заголовком `Content-Type: audio/wav`. Браузерный плеер понимает это автоматически.
2.  **Безопасность:** Внутри метода стоит `getCallWithSecurityCheck(id)`. Это значит, что если Юзер А попытается подставить ID звонка Юзера Б, бэкенд выдаст `403 Forbidden`. Это очень хорошо.
3.  **Доступность файлов:**
    - Для `original` путь прописывается сразу в методе `uploadFile`.
    - Для `redacted` путь прописывается **позже**, когда Python-сервер пришлет ответ. До этого момента вызов `/audio/redacted` вернет `404 Not Found`.

### 4. Как это использовать в UI (React/Vue/HTML)

Так как запросы защищены JWT-токеном, ты не можешь просто вставить ссылку в `<audio src="...">`. Тебе нужно сначала получить данные, а потом создать локальную ссылку.

**Пример на JavaScript:**

```javascript
async function playAudio(callId, type = "redacted") {
  const response = await fetch(`/api/calls/${callId}/audio/${type}`, {
    headers: {
      Authorization: `Bearer ${localStorage.getItem("token")}`,
    },
  });

  if (response.ok) {
    const blob = await response.blob();
    const url = window.URL.createObjectURL(blob);
    const audio = new Audio(url);
    audio.play();
  } else {
    console.error("Файл еще не готов или доступа нет");
  }
}

// Вызов для прослушивания очищенной версии
playAudio(15, "redacted");

// Вызов для прослушивания оригинала
playAudio(15, "original");
```

**Итог:** Функционал полностью готов. Бэкенд умеет различать типы файлов, проверять права доступа и стримить аудио в плеер. Твоя структура БД (хранение обоих путей в `CallRecord`) это отлично поддерживает.
